Use the user's existing Intel Mac mini running macOS and its working Docker Desktop installation. Separate backend responsibilities into accounts/access, menus, runs/requests and notifications without splitting them into independently deployed services. Reuse the approved project-owned Postcard Club React design system and maintain Storybook for every component's relevant states. Vite is the build/development tool rather than the production server.

Use the existing AWS DNS provider, expected to be Route 53, and an app subdomain pointing at the mini. Verify the hosted zone and inbound routing/firewall access to Caddy on 80/443. Caddy automatically issues/renews free public TLS certificates using Let's Encrypt, with its data persisted. Keep the database private to the deployment. Exact domain, addresses, account IDs, repository identity and version pins are setup configuration, not new product decisions.

GitHub Actions is the orchestrator for Terraform, automated host configuration, CI, releases and the accepted weekly/pre-migration backup flow. GitHub-hosted Linux jobs test and build `linux/amd64` images, publish to GHCR, then serialize deployments over host-key-verified SSH from passing `main`. Use a dedicated deployment identity, immutable release references, readiness/health checks, controlled migrations and recoverable prior images. Application rollback must account for database compatibility; do not imply reverting an image reverses a migration. First setup runs schema migrations and the accepted ORM initializer from runtime inputs, leaving initialized credentials/permissions unchanged on reruns. Operator recovery remains a separate explicit operation.

Brief maintenance outages are acceptable. Manual unlock/login after a cold macOS restart is accepted; automatically restore Docker Desktop/application services afterward and verify that sequence before relying on it. Restore-from-backup objective is one working day, subject to the mini or replacement host, network, recovery access and keys being available.

### API, authority and foreground updates

Use authenticated same-origin JSON HTTP endpoints. PostgreSQL is authoritative for saved state, permissions and durable work. Enforce the single active-run slot, request uniqueness and lifecycle/access changes through database constraints and transactions, with locking/conflict handling where required. Do not rely on frontend polling or background task timing to reject writes at/after a closing deadline. Races return clear rejections and refreshed authoritative state rather than silently reopening or changing terminal runs.

Refresh visible shared state roughly every five seconds and on focus, reconnection and successful actions. Keep relevant in-app notices deduplicated. Display server-derived deadlines in Europe/Belgrade; use authoritative instants for validation. Notification deep links load current state and recheck access. No persistent notification inbox or instant socket-update requirement is introduced.

### Sessions, scheduled work and push

Use revocable server-side opaque sessions backed by PostgreSQL, protected Secure/HttpOnly/SameSite cookies and CSRF protection. Sessions have a 30-day absolute lifetime, ending earlier on sign-out or applicable credential/access revocation. Device push registrations are tied to the session, so signed-out, expired or revoked sessions stop future delivery. Every operation and send rechecks current account/membership/permission eligibility; do not cache a revoked grant as continuing authority.

Persist notification intent/due work in PostgreSQL with the associated business transaction. The worker reconciles due deadlines and delivers eligible notifications, with durable claims/recovery, bounded useful retries, deduplication and stale-event suppression. Enforce one logical reminder per colleague/run while allowing its delivery to enabled devices. A crash around external dispatch can produce a duplicate push; do not promise exactly-once external delivery. Use no separate Redis/Celery service initially.

The normal required worker window is 08:00–15:00 office time, with processing continuing for outstanding runs/work after 15:00, including a run announced at 14:59. This is an availability requirement, not a new product prohibition on viewing or performing otherwise authorized actions outside that window; implementation may leave the idle process available on the mini. GitHub scheduled workflows do not handle minute-sensitive reminders. Use the agreed notification event/audience matrix, categories, private lock-screen wording, changed-deadline suppression/rescheduling and best-effort platform expectations. A database reconciliation after restart must not replay obsolete reminders.

### Terraform ownership and retained storage

Manage all applicable provider infrastructure through Terraform: backup and state S3 buckets in Frankfurt (`eu-central-1`), public-access blocking, encryption, state version history, required lifecycle settings, bucket/access policies, scoped IAM roles, GitHub OIDC trust and the app's DNS record. Reuse/import shared existing resources deliberately; do not recreate the domain/zone or duplicate an existing account-wide OIDC provider. Match OIDC trust to the actual repository identity and intended trusted branch/environment.

Use separate Terraform roots/states for retained foundation infrastructure and disposable application infrastructure. The foundation owns backup/state storage and its protection/access configuration; the app root references it. Configure `use_lockfile = true` for native S3 state locking and version the state bucket. Bootstrap the backend/trust using one authenticated operator session, then migrate initial state to protected remote storage and keep recovery independent of the mini. Terraform state remains sensitive even when application secret payloads are excluded.

Normal application `terraform destroy` must retain the foundation buckets and their contents. Use `prevent_destroy = true` and `force_destroy = false` for the retained buckets; verify foundation destroy planning fails while guards remain. This is a Terraform/configuration boundary, not immutable AWS Object Lock: removing resource configuration or using separate authorized AWS deletion can bypass it. Document an explicit full-retirement procedure rather than provide automatic bucket-emptying as normal teardown. The agreed backup expiry continues while buckets are retained. Preserve state history/current state and operator access independently of the backup expiration rule.

Compose and host automation own the mini's containers/volumes, host services, runtime files and Caddy configuration. Caddy owns TLS issuance/renewal and its private keys. Terraform does not manage the physical mini or retain application/TLS private-key values; these are the accepted automation boundaries, not omissions of provider-managed infrastructure.

### Backup and secret lifecycle

Take encrypted PostgreSQL-aware backups weekly and before migrations, retaining backup archives for 30 days. Gate migrations on a successful pre-migration backup/upload. This supersedes daily backups and the old 24-hour recovery-point assumption: approximately seven days of changes may be lost after a host/disk failure, potentially longer if scheduled jobs fail or are delayed. Monitor last successful backup age and failures, support manual retries, and test restoration before first use. Test effective retention/cleanup for any backup object versions; an expiring current object alone is not proof all older versions are removed. Keep Terraform state versions under their separate policy, never expire the current state as if it were a database archive.

Keep recoverable originals of database credentials, VAPID private keys, deployment SSH private keys and backup decryption identities in the operator's password manager. GitHub Actions secrets hold deployment copies of the required runtime/deployment values. Use a production environment if the GitHub plan supports it, otherwise repository secrets with trusted workflow/branch administration; do not assume unavailable approval features. Ordinary test/PR jobs receive synthetic values only. AWS access is temporary OIDC, with separate narrow infrastructure and backup roles.

Deploy secrets over verified SSH into a private directory outside the checkout, such as `~/Library/Application Support/coffee-app/secrets`. Restrict ownership/permissions, grant each container only the files it needs through Compose secrets, explicitly support file-based backend configuration and test actual Docker Desktop mount access. No secret payloads belong in source, image build layers/arguments, frontend bundles, Terraform inputs/state, artifacts or logs. State itself still requires protection. Public keys and non-secret configuration are ordinary configuration.

Use job-scoped GHCR credentials for publishing/pulling and discard host-side temporary registry authentication after deployment; validate Docker Desktop credential-helper cleanup instead of assuming a temporary config directory prevents Keychain persistence. The weekly backup job obtains OIDC credentials in Actions, invokes backup/public-recipient encryption on the mini over SSH, receives ciphertext and uploads it to S3.
