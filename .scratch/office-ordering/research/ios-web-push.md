# iOS Web Push feasibility

Checked: **2026-11-20**. Scope: the React 19/Vite **web app**, a future hosted HTTPS origin, FastAPI and PostgreSQL; no native application. Resolves [research ticket 04](../issues/04-ios-web-push.md). Platform facts below do not choose notification events or onboarding policy.

## Verified platform facts

**Feasible, with installation and opt-in.** iOS and iPadOS **16.4 or later** support standards-based Web Push for **Home Screen web apps**. An ordinary browser tab is not the supported iOS delivery surface. On older releases, a manifest with `display: standalone` or `fullscreen` establishes web-app behavior; a Home Screen bookmark alone is insufficient. Safari provides Add to Home Screen; third-party browsers can offer it too, so Safari is not the exclusive installation route. Actual third-party browser UI must be checked. [WebKit’s iOS announcement](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [released Safari 16.4 features](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/).

**Installation changed in iOS/iPadOS 26.** Any site added to Home Screen now opens as a web app by default, without a required manifest. Users can turn off **Open as Web App** and create a browser bookmark instead. A manifest remains useful for identity and icons; it is not universally required for installation on current systems. [WebKit Safari 26.0 release](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/#every-site-can-be-a-web-app-on-ios-and-ipados).

**Permission is explicit.** Request subscription directly from a user gesture, such as a button tap inside the installed app. Users can later change per-app notification settings. Focus can silence these notifications. Apple’s push service transports Web Push, but **no Apple Developer Program membership or separate native APNs account/certificate setup is required** for this standards-based route. [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Apple’s current subscription explanation](https://developer.apple.com/videos/play/wwdc2025/235/).

**Original Web Push requires a service worker.** Register and activate a worker on the application origin, acquire a subscription through its `pushManager`, use `userVisibleOnly: true`, and provide the application server’s public key. A `push` handler displays the notification with `showNotification`; silent pushes are prohibited and failure to display can revoke the subscription. This applies even when the page is open: a foreground-only UI update is not a substitute for displaying an original push notification. [WebKit’s original-versus-declarative explanation](https://webkit.org/blog/16535/meet-declarative-web-push/).

**Newer alternative:** iOS/iPadOS **18.4+** support **Declarative Web Push** for Home Screen web apps. It can subscribe through `window.pushManager` and display a structured notification payload without an installed worker; an optional worker can enhance it, with declarative display as fallback. Apple describes a backwards-compatible worker approach for older/non-supporting browsers. Therefore “all iOS push requires a worker” is outdated; supporting the 16.4 baseline still requires original Web Push handling. [Safari 18.4 release](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/), [Apple’s migration explanation](https://developer.apple.com/videos/play/wwdc2025/235/).

**Secure origin and subscription:** Push APIs are secure-context APIs. Use a valid HTTPS deployment for the phone; an HTTP LAN development address is not a production substitute. Worker script/scope must belong to the same origin. The subscription carries an endpoint and encryption material (`p256dh`, `auth`); subscriptions can change or deactivate, so they are not permanent user identifiers. The current Push API specification is a Working Draft, not a guarantee of implementation in every browser. [Push API specification](https://www.w3.org/TR/push-api/), [Service Worker origin and security rules](https://w3c.github.io/ServiceWorker/#security-considerations).

## Transport, delivery and operating limits

The server stores the subscription endpoint and keys against the colleague’s account and sends encrypted Web Push **POSTs to that endpoint**. Apple supports HTTP/1.1 or HTTP/2 over TLS, requires SNI, and documents outbound access to `https://*.push.apple.com`. Requests need VAPID authentication and TTL; the VAPID public key must match the subscription. Apple documents a 4 KB payload limit, expired-token responses (410), rate limits (429), and server failures. [Apple’s Web Push server requirements](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

Payload encryption is the Web Push encryption scheme, distinct from TLS; VAPID identifies the application server using its own key pair. These are web credentials, not native-app signing credentials. [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291.html), [RFC 8292](https://www.rfc-editor.org/rfc/rfc8292.html).

| App state | Supported expectation and boundary |
| --- | --- |
| Foreground | A push can be processed while the app is open. Original pushes still need a visible notification; in-app refresh is an additional behavior to implement. Exact banner/sound presentation is an OS/user-setting matter. |
| Background / screen locked | Push handling does not require a visible page; notifications can appear on the Lock Screen and in Notification Center, subject to permission and Focus. |
| Normally closed / no app window | Push is designed to work with the web app inactive; the page does not need a persistent connection. This is not a promise of arbitrary background execution or precise wake-up timing. |

The state expectations follow [Push API’s inactive-app model](https://www.w3.org/TR/push-api/), [WebKit’s display requirement](https://webkit.org/blog/16535/meet-declarative-web-push/), and [iOS notification integration](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/). No device test was performed here; force-quit, reboot and specific OS-version behavior remain acceptance tests, not established delivery guarantees.

**Best effort, not a deadline guarantee:** devices may be offline, permission can be removed, and push requests may expire or fail. Apple may store offline notifications for up to 30 days or less according to TTL, with limited offline storage. High urgency requests immediate delivery but does not guarantee it. [Apple delivery constraints](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers). The protocol allows early message expiry and subscription expiry; server acceptance does not establish that a colleague saw or acted on a message. [RFC 8030, delivery and expiration](https://www.rfc-editor.org/rfc/rfc8030.html#section-7). Apple also documents discarded notifications after acceptance; its native-app metrics console is not evidence that the account-free web route exposes equivalent telemetry. [Apple APNs metrics](https://developer.apple.com/documentation/usernotifications/viewing-the-status-of-push-notifications-using-metrics-and-apns).

## Proposed integration options — not decisions

- **Direct Python sender:** FastAPI accepts authenticated subscription registrations; PostgreSQL associates multiple installation subscriptions with an account. A Python Web Push library is a possible transport adapter: `pywebpush`’s own documentation supports subscription dictionaries, payload encryption and VAPID sending. This is evidence of fit, **not a selected dependency/version or a completed compatibility/security assessment**. [Maintainer documentation](https://github.com/web-push-libs/pywebpush).
- **Separate sender or managed provider:** FastAPI can hand notification work to another service that delivers standards-compliant encrypted Web Push to stored endpoints. This is an architectural option inferred from the application-server/push-service separation in [RFC 8030](https://www.rfc-editor.org/rfc/rfc8030.html#section-2); no vendor is selected or claimed compatible here.
- **Operational proposal:** keep PostgreSQL as the authority for runs and requests; treat notifications as hints to reload current state. A durable delivery job/outbox can isolate retries from request handling; remove expired endpoints, bound retries to useful TTL, and keep VAPID private keys server-side. These are proposed application safeguards, not an iOS mandate. Silent background synchronization must not be substituted for visible original push.

## Validation boundary and proposed acceptance checks

Playwright emulates viewport, user agent, touch and permissions; its patched WebKit is **not branded Safari or a real iPhone**. Its dedicated service-worker inspection support is documented for Chromium. A passing “Mobile Safari” project cannot establish Home Screen installation, the iOS permission sheet, Apple delivery, OS presentation or closed-app receipt. [Playwright emulation](https://playwright.dev/docs/emulation), [browser limitations](https://playwright.dev/docs/browsers#webkit), [service-worker tooling](https://playwright.dev/docs/service-workers).

Proposed automated coverage: use the frontend, FastAPI and PostgreSQL together to verify subscription ownership, registration/removal, denied/unsupported UI states, delivery-job creation, invalid/expired endpoints and retry policy. Separate mocked transport tests from any real push-service smoke test; neither is proof of iOS delivery. Verify worker/payload logic in a supported browser and component states in Storybook/unit tests when implemented.

Proposed **real iPhone/iPad acceptance** on the chosen minimum OS plus current OS: valid hosted HTTPS; add/open Home Screen app; tap to opt in; deny/revoke/re-enable; send while foregrounded, backgrounded, locked and normally closed; test force-quit/reboot separately; test offline/reconnect before and after TTL; check Focus/settings and notification-tap navigation to current run state. If both original and declarative paths are supported, cover both OS capability classes. Observe delivery and latency; do not turn one successful trial into a guarantee.
